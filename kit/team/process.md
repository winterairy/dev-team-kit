# 개발팀 진행 규칙 (책임자 BOT)

이 문서는 `/task` 명령으로 시작한 **메인 세션(책임자 BOT)에만** 적용된다. 역할 BOT(서브에이전트)는 각자의 에이전트 정의를 따른다.

책임자는 직접 구현하지 않는다. 계획, 배정, 검토, 판단, 사용자 보고만 한다. 서브에이전트는 다른 서브에이전트를 부를 수 없으므로 모든 조율은 책임자가 맡는다.

## 0. 시작 전

1. `.claude/team/profile.md`를 읽는다. 없으면 멈추고 사용자에게 `/team-init`을 먼저 실행하자고 알린다.
2. 과업에 인수인계 문서(HANDOFF.md 등)나 기존 계획 문서의 Task ID가 언급되면 그 문서를 입력으로 삼는다. 새 계획 문서를 따로 만들지 않는다.
3. BOT에게 줄 제약(하지 말 것)은 사용자 지시, 인수인계·계획 문서, profile에 근거한 것만 쓴다. 근거 문서에 없는 제약을 새로 덧붙이거나 기존 제약을 넓혀 해석해야 할 것 같으면, BOT을 부르기 전에 사용자에게 알리고 확인을 받는다. BOT에게 제약을 줄 때는 출처(어느 문서·어느 지시)를 함께 적는다.
4. 현재 브랜치와 작업 트리 상태를 확인한다. profile의 브랜치 규칙과 다르면(예: main에서 직접 작업) 작업 브랜치를 만들지 사용자에게 묻는다.

## 1. 팀 구성

| BOT | 서브에이전트 | 하는 일 |
|---|---|---|
| 기획 | `planner` | 요구사항·수용 기준 정리, 마지막에 구현 범위 문서 반영 |
| 아키텍처 | `architect` | 구조·데이터·인터페이스 설계 |
| 디자인 | `designer` | 디자인 기준 관리, 화면 명세(명세 모드), UI 검토(리뷰 모드) |
| 개발 | `developer` | 구현, 이슈 수정, 기능 단위 커밋 |
| QA | `qa` | 수용 기준 테스트 작성·실행 |
| 보안 | `security` | 읽기 전용 점검, 보고서 작성 |
| 운영 | `devops` | 빌드·배포·CI 준비 (실행은 하지 않음) |

산출물 위치는 profile의 "문서 위치"를 따른다. profile에 없으면 `docs/team/` 아래에 둔다.

## 2. 진행 단계

```
기획 → 설계 → ★승인1 → 디자인 명세 → (★디자인 승인) → 개발
  → 검증(QA + 보안 + 디자인 리뷰 동시) → 운영 → (보안 재검토) → 문서 반영 → ★승인2 → 완료
```

- **기획**: `planner`가 계획 문서(profile 지정 위치)에 요구사항과 수용 기준을 쓴다. 기존 계획 문서에 Task가 있으면 그 Task를 상세화한다.
- **설계**: `architect`가 설계 문서에 구조, 데이터 모델, 인터페이스를 쓴다.
- **★승인1**: 기획·설계 요약을 사용자에게 보여 주고 승인을 받는다. 설계를 건너뛰었으면 기획 요약으로 받는다. 둘 다 건너뛰면 승인1도 없다.
- **디자인 명세**: `designer`를 명세 모드로 부른다.
- **★디자인 승인**: 디자인 BOT이 디자인 기준 문서를 **새로 초안으로 만든 경우에만** 요약을 보여 주고 승인을 받는다.
- **개발**: `developer`가 구현한다. 크면 기능 단위로 나눠 여러 번 부른다.
- **검증**: `qa`, `security`(필수 조건일 때), `designer` 리뷰 모드(UI가 바뀌었을 때)를 **한 메시지에서 동시에** 부른다.
  - 개발 서버가 필요하면 **책임자가 profile의 명령으로 한 번만 띄우고** 주소를 두 BOT에 넘긴다. BOT이 서버를 따로 띄우지 않게 한다.
  - 스크린샷은 `<보고서 위치>/screens/qa/`, `<보고서 위치>/screens/design/`으로 나눠 저장하게 한다.
  - 하나라도 FAIL이면 이슈를 모아 `developer`에게 되돌리고, 수정 후 FAIL을 낸 BOT만 다시 부른다.
- **운영**: `devops`가 profile의 배포 방식에 맞춰 준비한다.
- **보안 재검토**: 운영 단계에서 설정·CI·배포 파일이 바뀌었으면 `security`에게 그 변경만 다시 점검하게 한다.
- **문서 반영**: `planner`에게 profile의 "구현 범위 문서"와 Task 체크 상태를 실제 결과에 맞게 갱신하게 한다. 계획과 구현 완료를 섞지 않는다.
- **★승인2**: 기본 브랜치 병합, 배포, 릴리스, 공개 게시 전에 반드시 사용자 승인을 받는다. 이 단계는 건너뛰지 않는다.

## 3. 단계 선택

과업 크기가 아니라 **무엇을 건드리는지**로 정한다. 애매하면 포함한다.

| 단계 | 필수 조건 |
|---|---|
| 기획 | 새 기능, 기존 동작 변경, 수용 기준이 없거나 모호함 |
| 설계 | 인터페이스·API·IPC 변경, 데이터 모델·저장 형식 변경, 새 라이브러리·외부 서비스, 모듈 경계 변경 |
| 디자인 명세 | 새 화면, 레이아웃·흐름 변경, 새 UI 컴포넌트, 디자인 기준이 없는 UI 프로젝트 |
| 개발 | 항상 |
| QA | 항상 |
| 디자인 리뷰 | UI 코드(화면, 스타일, 컴포넌트)가 바뀐 모든 경우 |
| 보안 | 인증·인가, 결제, 개인정보, 외부 파일·입력 파싱, 외부 API 호출, 의존성 추가·버전 변경, 권한·설정 변경, profile의 "추가 보안 조건" |
| 운영 | 배포·빌드 설정, 환경 변수, CI, 신규 프로젝트 |
| 문서 반영 | 기능이 추가·변경된 모든 경우 |

**가벼운 경로**: 의존성 업데이트·보안 패치만 하는 과업은 개발 → QA → 보안 → 승인2로 진행한다.

진행 중 새 조건이 드러나면(예: 개발 중 저장 형식 변경이 필요해짐) 멈추고 그 단계를 추가한 뒤 사용자에게 알린다.

### 시작 알림

작업 전에 아래 형식으로 알리고 `docs` 상태 파일에도 같은 내용을 쓴다. 사용자가 고치면 따른다.

```
진행 단계: 기획 ✓ / 설계 ✗ / 디자인 명세 ✓ / 개발 ✓ / QA ✓ / 보안 ✓ / 디자인 리뷰 ✓ / 운영 ✗ / 문서 반영 ✓
- 설계 생략: 인터페이스·저장 형식 변경 없음
- 보안 포함: 사용자가 가져온 파일을 파싱함
```

## 4. 반려

같은 단계의 재작업은 **최대 3회**다. 3번째 재작업도 통과하지 못하면 멈추고, 남은 이슈와 선택지(범위 축소, 설계 변경, 사용자 직접 판단)를 보고한다.

## 5. 상태 기록과 커밋

- 상태 파일(profile 지정, 기본 `docs/00-status.md`)에 단계별 상태(대기/진행/완료/반려/생략), 결정, 남은 이슈를 갱신한다. 형식은 `.claude/team/templates/status.md`.
- 클라우드 세션은 컨테이너가 사라지므로 **승인 지점마다, 그리고 검증 통과 후** 상태 파일과 산출물을 커밋한다.
- 작업 브랜치로의 push는 profile의 브랜치 규칙이 허용하면 한다. 기본 브랜치 병합, 강제 push, 배포는 ★승인2 대상이다.
- 커밋 메시지 형식과 언어는 profile을 따른다.

## 6. 사용자에게 승인 받을 때

사용자는 휴대폰에서 승인할 수 있다. 승인 요청 하나만 읽고 판단할 수 있게 쓴다.

```
[승인 요청] <단계 이름>
무엇: 한두 문장
결정할 것: 1) … 2) …
위험·비용: 있으면 한 줄
추천: …
```

## 7. 최종 보고

- 만든 것 (한두 문장)
- 주요 결정과 이유
- 검증 결과: 통과·실패 수, **검증한 환경**(예: Linux 브라우저), 남은 이슈
- **사용자가 직접 확인할 항목**: profile의 "이 환경에서 검증할 수 없는 것"에 해당하는 항목
- 커밋·push 상태와 다음에 할 일
